# ADR-0001: Используем потоковую распределённую архитектуру

## Статус

Принято

## Контекст

Система телеметрии должна принимать данные от более чем 1000 хостов и
микросервисов с общим потоком 100 000-200 000 метрик в секунду и выдерживать
кратковременные всплески нагрузки.

Ключевые требования:

- подтверждённые метрики не должны теряться;
- последние значения должны быть доступны с минимальной задержкой;
- исторические данные должны быть доступны для аналитики;
- алерты должны формироваться в реальном времени;
- отказ отдельного компонента не должен останавливать всю систему;
- приём, обработка, хранение и запросы должны масштабироваться независимо.

Модульный монолит проще в разработке и эксплуатации на старте, но для данного
потока данных он создаёт риск общего bottleneck, усложняет независимое
масштабирование этапов и повышает blast radius при отказах.

## Решение

Используем потоковую распределённую архитектуру с разделением системы на
логические этапы:

- приём и валидация метрик;
- надёжная буферизация входящего потока;
- нормализация и агрегация;
- вычисление правил алертинга;
- запись в хранилища последних, исторических и архивных данных;
- API для запросов и интеграции с системами визуализации.

Компоненты взаимодействуют через надёжный поток данных, а не через синхронную
цепочку вызовов для каждой метрики. Это позволяет сглаживать всплески,
повторно обрабатывать ранее принятые данные и масштабировать отдельные этапы
конвейера независимо.

Конкретные технологии потоковой доставки, хранения и вычислений фиксируются в
отдельных ADR. Этот ADR определяет архитектурный стиль, а не выбор конкретного
продукта.

## Последствия

Плюсы:

- приём данных отделён от скорости последующей обработки;
- проще выдерживать всплески нагрузки;
- можно масштабировать приём, обработку, хранение и запросы независимо;
- отказ отдельного этапа не обязан приводить к потере уже принятых данных;
- появляется естественная возможность повторной обработки;
- архитектура хорошо соответствует real-time алертингу и исторической
  аналитике.

Минусы:

- выше инфраструктурная сложность по сравнению с монолитом;
- требуется дисциплина в контрактах сообщений и версионировании форматов;
- сложнее отладка end-to-end сценариев;
- нужно явно решать вопросы идемпотентности и дубликатов;
- consistency между последними, агрегированными и историческими данными может
  быть eventual, а не строго синхронной.

## Альтернативы

### Модульный монолит

Отклонён для основной платформы из-за требований к пропускной способности,
отказоустойчивости и независимому масштабированию этапов конвейера.

### Набор синхронных микросервисов без потокового буфера

Отклонён, потому что синхронная цепочка увеличивает задержку приёма, хуже
переносит всплески и повышает риск потери данных при отказе downstream
компонентов.
