# ADR-0002: Используем многоуровневое хранение на PostgreSQL, Redis, ClickHouse и MinIO

## Статус

Принято. Дата: 2026-01-20.

## Контекст

Архитектурный стиль зафиксирован в ADR-0001: потоковая распределённая система с
независимо масштабируемыми этапами приёма, обработки, хранения и запросов.
Конкретные технологии хранения этим ADR не определялись.

Нагрузка и профиль данных:

- более 1000 активных источников (хосты, микросервисы, приложения);
- 100 000–200 000 метрик в секунду в штатном режиме;
- всплески до 400 000 метрик в секунду на 5 минут (deploy storm, инцидент);
- разные классы данных с разными профилями доступа.

Классы данных:

| Класс | Профиль доступа | Ключевое требование |
| --- | --- | --- |
| Конфигурация и состояние: источники, определения метрик, политики агрегации, правила алертинга, состояние алертов | редкая запись, частые точечные чтения, транзакции | согласованность, ссылочная целостность |
| Последние значения временных рядов | очень частые чтения, запись на каждое измерение | задержка p95 <= 500 мс (FR-011, FR-014) |
| Исторические измерения и агрегаты | диапазонные сканы, агрегации, редкие записи батчами | сжатие, скорость сканирования (FR-012, FR-015) |
| Архив | почти не читается, хранится долго | стоимость хранения, целостность (FR-013) |
| Транспорт между этапами | последовательное чтение, replay | durability, повторная обработка (FR-005, FR-017) |

Ограничения:

- система разворачивается самостоятельно (self-hosted, Kubernetes), без
  привязки к облачному вендору;
- приоритет open-source решений со зрелой экосистемой и воспроизводимым локальным
  стендом;
- после подтверждения приёма данные не должны теряться (NFR durability);
- повторная обработка ранее принятых данных обязана быть идемпотентной
  (BR-011);
- политики хранения настраиваются отдельно для оперативных, исторических и
  архивных данных (NFR retention).

Ключевое наблюдение: **не существует одного хранилища, одновременно оптимального
для миллисекундного доступа к последним значениям, дешёвого сканирования
терабайтов истории и долговременного архива.** Попытка взять одно хранилище
приводит либо к недопустимой задержке, либо к недопустимой стоимости.

## Решение

Принимаем многоуровневое хранение: каждый класс данных обслуживается хранилищем,
оптимальным для его профиля доступа, а согласованность между уровнями
обеспечивается идемпотентной записью через Storage Writer.

| Класс данных | Хранилище | Роль | Срок хранения |
| --- | --- | --- | --- |
| Конфигурация, состояние алертов, операционные записи | PostgreSQL 16 | system of record | постоянно; `alert_event`, `processing_failure` — 90 дней |
| Последние значения, короткое горячее окно | Redis 7 / Redis Stack (RedisTimeSeries), инстанс `latest` | hot-слой | последнее значение всегда; окно — до 15 минут |
| Результаты тяжёлых запросов | Redis, инстанс `cache` | L2-кэш (L1 — Caffeine в Query Service) | TTL 5–60 секунд |
| Исходные измерения и агрегаты | ClickHouse | warm-слой, OLAP | raw — 7 дней, агрегаты 1s — 30 дней |
| Архив (1m/1h и старше) | MinIO + Parquet | cold-слой | 1 год и более, настраивается |
| Транспорт и replay | Kafka | durable log, не system of record | 7 дней |

Физическая модель описана в `spec/database.dbml` и разложена по схемам
`meta` (PostgreSQL), `ts` (ClickHouse), `latest` (Redis), `archive` (MinIO).

### PostgreSQL: конфигурация и состояние

- Схема `meta`: `telemetry_source`, `metric_definition`, `aggregation_policy`,
  `alert_rule`, `alert`, `alert_event`, `processing_failure`, `replay_job` и
  таблицы-словари для `map`/`list`-полей.
- Причины выбора: ACID, внешние ключи и уникальные ограничения — именно здесь
  сосредоточены бизнес-инварианты (BR-001, BR-009, BR-015, INV-004);
  объём данных — единицы гигабайт, нагрузка на чтение умеренная;
  административные изменения редки и требуют транзакционности.
- Партиционирование `alert_event` и `processing_failure` по месяцам,
  TTL-политика удаления старых партиций.
- HA: primary + streaming replica, PgBouncer для пула соединений,
  резервное копирование WAL (pgBackRest).

### Redis: последние значения и кэш

- **Два независимых инстанса, а не один с разными префиксами ключей**: политика
  вытеснения задаётся на инстанс, а не на ключ.
  - `latest` — `maxmemory-policy noeviction`, AOF `everysec`: потеря последнего
    значения из-за вытеснения недопустима (FR-011).
  - `cache` — `allkeys-lru`: кэш результатов запросов, потеря допустима.
- RedisTimeSeries, ключ — `TimeSeries.fingerprint`; запись `TS.ADD` с
  `ON_DUPLICATE LAST` и проверкой `observed_at` (Lua-скрипт): более старое
  измерение не заменяет более новое (BR-010, INV-003).
- `RETENTION` задаётся на ключ; окно горячих данных ограничено 15 минутами для
  приоритетных рядов (обоснование — в разделе о ёмкости).
- Redis также хранит короткоживущие ключи дедупликации и подавления алертов
  (TTL), но источником истины по алертам остаётся PostgreSQL.
- HA: Redis Cluster / Sentinel, hash tags по fingerprint для локальности.

### ClickHouse: исторические данные

- Таблицы `ts.time_series` (измерения), `ts.metric_sample` (исходные точки),
  `ts.metric_aggregate` (агрегаты).
- Движок `ReplicatedReplacingMergeTree` (ClickHouse Keeper), порядок сортировки
  `(metric_definition_id, fingerprint, observed_at)`, партиционирование
  `toDate(observed_at)`.
- Сжатие: `CODEC(Delta, ZSTD(1))` для временных меток, `CODEC(Gorilla, ZSTD(1))`
  для значений — типично 1,5–3 байта на точку.
- Идемпотентность: `insert_deduplication_token = correlation_id` плюс
  `ReplacingMergeTree`; агрегаты уникальны по
  `(policy, источник, набор меток, функция, начало окна)`.
- Запись только батчами (1–5 МБ или не реже раза в секунду): мелкие вставки
  порождают проблему «too many parts».
- `TTL observed_at + INTERVAL 7 DAY` для raw и `+ INTERVAL 30 DAY` для 1s;
  удаление — только после успешного архивирования (FR-013).
- Шардирование по `cityHash64(fingerprint)`, репликация RF=2 на стенде, RF=3 в
  production-профиле.

### MinIO: архив

- Бакет `telemetry-archive`, Parquet + ZSTD, разбиение
  `dt=YYYY-MM-DD/resolution=1m|1h/metric=<name>/part-*.parquet`.
- Каталог архивных объектов ведётся в `meta.archive_object` (PostgreSQL):
  ключ объекта, диапазон, число записей, размер, checksum, статус.
- Данные удаляются из ClickHouse только после `status = COMPLETED` и проверки
  checksum; ошибки архивирования фиксируются и допускают повторный запуск.
- S3-совместимый API оставляет возможность заменить MinIO на облачное
  объектное хранилище без изменения кода.

### Kafka: граница ответственности

Kafka обеспечивает durable-буфер и replay (FR-005, FR-017), но **не является
system of record**: retention топиков ограничен, произвольные аналитические
запросы невозможны. Топики, партиционирование и семантика exactly-once
фиксируются отдельным ADR; здесь фиксируется только ограничение на его
результат: ключ партиционирования должен сохранять порядок измерений одного
временного ряда, иначе последнее значение будет вычисляться неверно.

### Запись и согласованность

1. Storage Writer читает `metrics.raw` / `metrics.1s` / `metrics.1m` и пишет в
   ClickHouse (батчами) и Redis (условная запись последнего значения).
2. Доставка — at-least-once, все записи идемпотентны по естественным ключам
   (BR-011): повторная обработка не создаёт дубликатов и не меняет результат.
3. Между уровнями согласованность **eventual**: Redis может отставать от
   ClickHouse на доли секунды. Целевая задержка актуализации — p95 <= 5 с (NFR).
4. Query Service сам выбирает уровень: последние значения — Redis, диапазоны до
   30 дней — ClickHouse, старше — MinIO; результаты кэшируются (Caffeine, затем
   Redis `cache`). Пользователь видит единый источник данных.

### Ёмкость (оценка порядка величины)

Расчёт для 200 000 метрик/сек, 1–2 млн активных временных рядов:

| Уровень | Расчёт | Оценка |
| --- | --- | --- |
| ClickHouse, raw | 17,3 млрд точек/сутки x 1,5–3 Б, 7 суток | 180–360 ГБ |
| ClickHouse, 1s-агрегаты | ~17 млрд точек/сутки x 1,5–3 Б, 30 суток | 0,8–1,5 ТБ |
| Redis `latest` | 1–2 млн ключей по ~200 Б | 0,2–0,5 ГБ |
| Redis, горячее окно 15 мин | 100 тыс. приоритетных рядов x 900 точек x ~32 Б | 3–6 ГБ |
| MinIO, 1m/1h за год | Parquet + ZSTD | 0,2–0,5 ТБ |

Отдельно фиксируем ограничение: **полное 24-часовое горячее окно исходных
точек в Redis нереализуемо** — 17,3 млрд точек требуют не менее 0,5 ТБ RAM.
Поэтому «горячими» считаются последние значения всех рядов и короткое окно
приоритетных рядов; запросы за 24 часа обслуживает ClickHouse с кэшем, что
укладывается в целевые p95 (исторические запросы <= 3 с, последние значения
<= 500 мс).

На демонстрационном стенде нагрузка и объёмы масштабируются коэффициентом
порядка 1/100 без изменения архитектуры.

## Последствия

Плюсы:

- каждый класс данных обслуживается хранилищем, оптимальным по задержке и
  стоимости;
- миллисекундный доступ к последним значениям не конкурирует с аналитикой;
- сжатие и партиционирование ClickHouse делают 30-дневную историю экономичной;
- архив в Parquet не требует дорогого OLAP-кластера и доступен для offline-
  аналитики;
- идемпотентность и replay наследуются от потоковой архитектуры (ADR-0001);
- отказ одного хранилища деградирует только соответствующий класс запросов.

Минусы:

- четыре хранилища и Kafka — заметная эксплуатационная сложность: бэкапы,
  мониторинг, обновления, ёмкостное планирование для каждого;
- согласованность между уровнями eventual, а не строгая;
- требуются фоновые процессы: downsampling, архивирование, TTL, сверка
  каталога архива;
- Query Service вынужден содержать планировщик запросов и слияние результатов;
- рост кардинальности меток (числа уникальных наборов) дороже всего бьёт по
  ClickHouse и Redis.

Риски и меры:

| Риск | Мера |
| --- | --- |
| Вытеснение последних значений из Redis | отдельный инстанс `noeviction` + AOF + восстановление из Kafka/ClickHouse |
| «Too many parts» в ClickHouse | батчинг записи, контроль размера партиций, alert на delay вставки |
| Расхождение горячего и исторического слоёв | алерт на лаг репликации, целевой p95 актуализации 5 с |
| Удаление данных до успешного архива | статус `archive_object` + checksum как условие удаления |
| Взрыв кардинальности меток | `allowedLabelKeys` (BR-008), лимиты на пакет и на число рядов, мониторинг |
| Рост стоимости хранения | лестница downsampling raw -> 1s -> 1m -> 1h, TTL по уровням |

## Альтернативы

### Единое хранилище ClickHouse для всех классов данных

Отклонено: ClickHouse не даёт миллисекундного доступа к последним значениям при
заявленной нагрузке, а хранение оперативной конфигурации и состояния алертов в
нём лишает систему транзакционных гарантий и ссылочной целостности. Кроме того,
TTL-удаление истории не заменяет управляемый архив с проверкой целостности.

### PostgreSQL + TimescaleDB как единое time-series хранилище

Отклонено: при 200 000 записей/с и 30-дневной истории аналитические сканы и
сжатие уступают колоночному ClickHouse, а масштабирование записи и хранения
требует заметно большего числа узлов. PostgreSQL остаётся, но только для
метаданных, где он силён.

### InfluxDB (open-source)

Отклонено: горизонтальное масштабирование открытой версии ограничено, а
аналитические запросы по десяткам миллиардов точек уступают ClickHouse;
дополнительный плюс ClickHouse — привычный SQL и экосистема.

### Elasticsearch / OpenSearch

Отклонено: стоимость хранения и память на точку существенно выше, а
time-series-агрегации и сжатие уступают колоночному движку; лишний компонент
ради задач, которые решает ClickHouse.

### Cassandra / ScyllaDB

Отклонено: отличная запись, но нет ad-hoc аналитики и оконных агрегаций;
потребовался бы отдельный аналитический слой, то есть хранилищ стало бы больше.

### Redis как основное историческое хранилище

Отклонено: стоимость RAM на терабайты истории, persistence не заменяет
настоящее хранилище, аналитика ограничена.

### Kafka (в том числе с tiered storage) как единственное хранилище

Отклонено: ограниченный retention, отсутствие произвольных запросов, нет
эффективного сканирования по меткам и диапазонам. Kafka остаётся транспортом и
источником повторной обработки, но не system of record.

### MongoDB для метаданных

Отклонено: для конфигурации и состояния нужны транзакции и строгие связи между
сущностями; документная модель не даёт выигрыша при текущем объёме.

### Облачное S3 вместо MinIO

Не отклонено, а отложено: MinIO выбран для self-hosted стенда, но S3-совместимый
API сохраняет возможность переезда без изменения кода.

## Открытые вопросы

- Провести нагрузочный POC: подтвердить 400 000 метрик/с на 5 минут,
  коэффициент сжатия ClickHouse и фактическую задержку актуализации Redis.
- Уточнить число шардов ClickHouse и профиль репликации (RF=2 vs RF=3) для
  целевого стенда.
- Выбрать ClickHouse Keeper или внешний ZooKeeper.
- Зафиксировать RPO/RTO и процедуру восстановления каждого хранилища.
- Подтвердить ёмкость горячего окна Redis на реальной кардинальности меток.
- Отдельный ADR: топология Kafka (партиции, retention, exactly-once).
