# ADR-0004: Avro и реестр схем для внутренних событий Kafka

## Статус

Принято. Дата: 2026-11-04.

## Контекст

Внутренний поток должен выдерживать не менее 200 000 измерений/с (NFR-PERF-001),
а потребители должны читать сообщения прежних версий при повторной обработке
(FR-017). Логические контракты четырёх событий описаны в `spec/events.yaml`,
но сами по себе не являются исполняемыми схемами.

## Решение

- Внутренние события Kafka кодируются **Avro**. Для каждого типа события
  (`MetricAccepted`, `MetricNormalized`, `MetricAggregateCalculated`,
  `AlertStateChanged`) ведётся своя версия схемы, а не одна схема на весь поток.
- Используется размещённый в собственной инфраструктуре **Apicurio Registry**.
  Каждая запись Kafka несёт идентификатор конкретной зарегистрированной схемы;
  потребитель выбирает схему по этому ID, а не по имени топика или только по
  полю `schemaVersion`. Способ бинарного framing ID подлежит утверждению.
- Для схем каждого типа в реестре действует **BACKWARD_TRANSITIVE**: новая версия
  должна читать все ранее зарегистрированные версии, которые могут встретиться
  при replay. Приём не устраняет необходимость координировать обновления:
  старый потребитель может не прочитать новое сообщение до своего обновления.
- Исходные `.avsc` хранятся и версионируются в репозитории; CI проверяет
  валидность схем и совместимость с предыдущими версиями, а регистрация
  проверенных схем выполняется при развёртывании до запуска отправителей.
  Сервисы кэшируют схемы и не обращаются в реестр для каждой точки.
- Внешний протокол агента относится к OpenAPI и **не** определяется этим ADR.
  Parquet-архив MinIO также не обязан повторять бинарное представление Avro.

## Границы решения

Структура исполняемых `.avsc`, точный framing ID, кодирование UUID, decimal и
времени, представление nullable-полей и правила обработки отсутствующей схемы
при недоступном реестре ещё требуют согласования (EVQ-005). До этого примеры
в `spec/events.yaml` остаются иллюстрациями, а не wire-контрактом.
