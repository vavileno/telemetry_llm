# ADR-0005: Ключи партиционирования внутренних событий Kafka

## Статус

Принято. Дата: 2026-11-05.

## Контекст

Повторные отправки измерения сохраняют `measurementId` (BR-011); конфликт
содержимого по нему проверяется после приёма, до доменных эффектов (BR-033).
Для нормализации и агрегации требуется группировка по ряду или политике,
а события одного алерта относятся к одному `alertId`. Один ключ на все
этапы эти задачи не решает.

## Решение

| Поток | Логический ключ Kafka | Гарантируемая область порядка внутри партиции |
| --- | --- | --- |
| `metrics.raw` (`MetricAccepted`) | `measurementId` агента | публикации одной точки, в том числе повторы и конфликтующие версии |
| `metrics.normalized` (`MetricNormalized`) | `timeSeriesFingerprint` по определению метрики, источнику и нормализованным меткам (BR-009) | точки одного нормализованного ряда |
| потоки агрегатов (`MetricAggregateCalculated`) | группа агрегации: `policyId`, `metricDefinitionId`, `sourceId` при наличии и нормализованные метки группировки | результаты одной политики/группы; функция и окно не часть ключа |
| `alerts` (`AlertStateChanged`) | `alertId` | события одного алерта |

Разные ключи на этапах обработки означают перегруппировку после проверки
исходной точки. Kafka направляет сообщения с одинаковым ключом в одну
партицию топика, **но не сравнивает содержимое и не дедуплицирует точки**.
Storage Writer не может записывать `metrics.raw` в историю в обход проверки
по `measurementId` (BR-033); способ доставки проверенных данных и согласования
потребителей остаётся открытым (EVQ-010). Повторы с одним ID нужно
сопоставлять до перегруппировки по ряду, даже если в конфликтующем сообщении
изменились метки или источник.

## Границы решения

Число партиций, топология дополнительных потоков, бинарное кодирование
составных ключей (включая nullable `sourceId` и порядок меток), версия
алгоритма fingerprint, RF/acks/min ISR и retention пока не утверждены
(EVQ-005/006/010). Перераспределение партиций может менять фактический
порядок во время миграции; для доменной корректности по-прежнему нужны
проверка ID, сравнение времени для latest и сериализация переходов алерта.
