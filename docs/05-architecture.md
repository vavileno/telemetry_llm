
# Архитектура системы телеметрии

Статус: **проектный вариант на уровне контейнеров и компонентов**. Источники
требований: [`system.yaml`](../spec/system.yaml),
[`requirements.yaml`](../spec/requirements.yaml),
[`non-functional-requirements.yaml`](../spec/non-functional-requirements.yaml),
[`business-rules.yaml`](../spec/business-rules.yaml) и
[`use-cases.yaml`](../spec/use-cases.yaml). Принятые решения:
[`ADR-0001`](../adr/0001-architecture-style.md) (потоковая архитектура) и
[`ADR-0002`](../adr/0002-database-choice.md) (классы хранилищ). Этот документ
описывает **предлагаемую декомпозицию**, но не объявляет новые технологии,
протоколы или гарантии транзакций утверждёнными ADR.

## Движущие требования и границы

- Более 1000 источников, 200 000 измерений/с в штатном режиме, целевой всплеск
  400 000 измерений/с на 5 минут; приём, обработка и запросы масштабируются
  независимо (NFR-PERF-001/002, NFR-SCALE-001/002).
- Подтверждение приёма — только после устойчивой фиксации; задержка доступности
  последнего значения p95 ≤ 5 с, формирование события алерта p95 ≤ 10 с;
  запрос latest p95 ≤ 500 мс, истории за 24 ч p95 ≤ 3 с в пределах лимитов
  (FR-004, NFR-PERF-003–006).
- Подтверждённые данные не теряются при отказе одного экземпляра; повторы,
  ошибки обработки и replay не создают неконтролируемых доменных дубликатов
  (FR-005, FR-017/018, BR-011, NFR-REL-001–005).
- Неизвестный источник не создаётся при передаче метрик; права отправителя
  проверяются для конкретного зарегистрированного источника (FR-021/022).
- Внутри системы только метрики и их агрегаты; логи и трассы наблюдаемых
  приложений, доставка уведомлений и полноценное управление инцидентами — вне
  границ (`system.yaml`, `scope`). Собственные логи и трассировка платформы
  относятся к её эксплуатации.

## Представления архитектуры

- [Контекст](../diagrams/context.mmd): пользователи, источники и внешние системы.
- [Контейнеры](../diagrams/containers.mmd): отдельно масштабируемые процессы,
  шина и хранилища. Стрелки задают направления, а не готовые API-контракты.
- [Компоненты](../diagrams/components.mmd): ответственности **внутри**
  контейнеров и границы владения данными. Компонент не равен отдельному pod.
- [Каталог сервисов](services/README.md): отдельные описания ответственности,
  отказов и эксплуатационных проверок по контейнерам.
- [Модель данных](../spec/database.dbml): логические связи между хранилищами;
  DBML не является исполняемой миграцией для Redis/ClickHouse/MinIO.

## Контейнеры и владельцы

| Контейнер | Внутренние компоненты / ответственность | Зависимости и данные | Основные требования |
| --- | --- | --- | --- |
| Ingestion Service | приём пакетов, аутентификация и привязка отправителя, валидация источника и метки, лимиты и управление перегрузкой, публикация без изменения исходного содержания | читает справочники из PostgreSQL через разрешённый интерфейс; пишет только `metrics.raw` в Kafka | FR-001–005, FR-022; UC-001 |
| Processing Service | нормализация, создание устойчивого идентификатора ряда, учёт event time и поздних точек, оконные агрегаты, изоляция ошибок | читает `metrics.raw`, политики из конфигурации, публикует обработанные точки и агрегаты в Kafka | FR-006–008, FR-018; BR-006–014 |
| Alerting Service | загрузка версий правил, оценка окон, переходы состояний, атомарная фиксация состояния и AlertEvent | читает обработанный поток/агрегаты; PostgreSQL — авторитетный источник состояния; публикует через outbox | FR-009/010/023; UC-006/009 |
| Storage Writer | пакетная запись исходной истории и агрегатов, условное обновление latest, повторные попытки и сверка результатов | Kafka (`metrics.raw` и обработанные потоки) → ClickHouse и Redis `latest`; дедупликация по согласованным ключам | FR-011/012, BR-010/011 |
| Query Service | валидация и авторизация, планировщик по диапазону, лимиты запросов, объединение и форматирование результата | Redis `latest`/`cache`, ClickHouse, архив MinIO при поддержке чтения | FR-014–016/020; UC-002–004 |
| Control Service | административные операции над источниками, определениями, политиками, правилами, алертами, проблемными данными и заданиями replay; аудит | PostgreSQL — source of truth; вызывает управляемые операции обработки, не вставляет метрики напрямую | FR-009/017/018/020/021/023; UC-005/008/009 |
| Replay Worker | выбор доступного диапазона, контроль прогресса, повторная публикация с сохранением идентичности исходных данных | Kafka/архив по доступности и политике; PostgreSQL для ReplayJob | FR-017/018; UC-008 |
| Archive Worker | управляемый downsampling и выгрузка, проверка контрольной суммы, каталог и удаление только после подтверждения | ClickHouse → MinIO; каталог архива в PostgreSQL | FR-013, NFR-DUR-002/003 |
| Event Dispatcher | публикация сохранённых событий алерта из outbox; повторные попытки | PostgreSQL outbox → Kafka `alerts`; дальнейшая доставка — внешний адаптер/система | FR-010/023; BR-018/019 |
| Адаптер внешних событий | передача событий во внешнюю систему уведомлений/инцидентов, ограниченные повторы и изоляция сбоев интеграции | читает Kafka `alerts`; внешний протокол определяется контрактом интеграции | FR-010, NFR-REL-003 |

**Граница конфигурации.** Control Service — единственная точка изменения
конфигурации через административный интерфейс; Ingestion/Processing/Alerting
используют чтение или версии снимков с контролем актуальности. Права чтения и
администрирования разделены. Способ выдачи удостоверений и распределения прав
остаётся открытым до ADR-0003. `allowedLabelKeys` ограничивает допустимые
пользовательские ключи (BR-008); отдельное административное управление метками
и их значениями в текущих требованиях **не задано**. Нельзя превращать это в
неявную регистрацию каждой метки при приёме.

**Граница интеграций.** Grafana и аналитические клиенты обращаются к Query
Service; внешняя система уведомлений и управления инцидентами потребляет
события через адаптер, но правила доставки и каналы принадлежат ей. Обещать
прямой совместимый API Grafana нельзя до OpenAPI и выбора адаптера.

## Основные сценарии и гарантии

### Приём и обработка (UC-001, FR-001–008)

1. Ingestion аутентифицирует отправителя, проверяет его право на `sourceId`,
    статус источника, обязательные поля, разрешённые ключи меток и лимиты;
    неизвестный источник и метрика от чужого источника отклоняются без
    саморегистрации. Агент создаёт стабильный `measurementId` для каждой точки
    и сохраняет его при повторах; совпадение времени у разных точек допустимо.
    При недоступной проверке прав приём не подтверждается.
2. Валидное измерение публикуется в устойчивый входной поток Kafka. Успех
    возвращается **для каждой точки с `measurementId` после подтверждения её
    устойчивой записи в Kafka** по выбранной политике репликации. Пакет может
    завершиться частичным успехом: отказ одной точки не откатывает другие.
    Ответ агенту содержит два списка: подтверждённо принятые точки и точки без
    подтверждения с причиной и признаком возможности повтора. Каждая запись
    содержит позицию в пакете и корректный `measurementId`, если он есть;
    каждая позиция находится ровно в одном списке. При тайм-ауте записи
    неизвестный исход указывается во втором списке; он не доказывает отсутствие
    точки в потоке. Агент повторяет неподтверждённые точки
    с прежним ID. Задержка downstream не меняет смысл подтверждения, но при
   исчерпании буфера включается ограничение приёма (FR-005).
3. Processing читает вход, нормализует метрику, детерминированно вычисляет
    идентичность ряда из определения, источника и нормализованных меток.
    `measurementId` проходит обработку неизменным; `eventId` различает события,
    а `correlationId` нужен для диагностики, не для дедупликации точек.
   Исходный поток не перезаписывается. Поздние/SUSPECT точки маршрутизируются
   по BR-006/007/010; ошибки изолируются, а не блокируют независимые данные.
4. Processing публикует обработанные точки и агрегаты. Storage Writer сохраняет
   исходную историю из `metrics.raw` и агрегаты пакетами в ClickHouse; из
    обработанного потока условно обновляет Redis последним **валидным по event
    time** значением ряда. Если нормализация изменила представление точки,
    исходные поля должны оставаться восстановимыми из исторической записи;
    история сохраняет `measurementId`. Дедупликация по нему требует явного
    механизма записи/чтения: ClickHouse не обеспечивает её мгновенно одним
    объявлением PK. Точный формат пока не определён. Alerting Service оценивает только
   разрешённые правила и релевантные данные.

Предлагаемые имена логических потоков: `metrics.raw`, `metrics.normalized`,
`metrics.1s`, `metrics.1m`, `alerts`, плюс поток изоляции ошибок. Это **не
событийные контракты**: схемы сообщений, версия, ключ партиционирования,
retention и режим подтверждения требуют `spec/events.yaml` и отдельного ADR
по Kafka. Порядок измерений одного ряда желателен, но correctness latest
обеспечивается атомарным сравнением event time, не предположением о порядке
доставки.

### Алерты и ручной сброс (UC-006, UC-009)

- Автоматическая оценка переводит алерт по допустимым переходам BR-017;
  событие возникает **только при изменении состояния** (BR-018). Если условия
  не изменились, новое событие не создаётся.
- Control Service проверяет административное право и состояние `FIRING`;
  ручной сброс переводит в `RESOLVED`, не отключая правило. Автор и время
  сохраняются в контексте события, повторы не создают второе событие.
- Состояние Alert, AlertEvent и запись outbox фиксируются **в одной транзакции
  PostgreSQL** с блокировкой или optimistic concurrency. Подтверждать
  административный сброс до фиксации нельзя. Dispatcher публикует событие
  асинхронно; его повторная публикация возможна, потребитель дедуплицирует по
  `eventId = AlertEvent.id` (неизменен при повторе). Успех операции означает
  сохранённое событие и запись outbox, **не**
  подтверждённую доставку во внешнюю систему.
- Сбой уведомителя не отменяет уже совершённый переход состояния. Если после
  ручного сброса условие продолжает выполняться, следующее срабатывание
  определяется обычной оценкой правил, без неоговорённого suppression.

### Запросы, архив и replay (UC-002–004, UC-008)

- Последние значения: Redis `latest`; ограниченный исторический диапазон:
  ClickHouse (полные исходные точки — одни сутки от `receivedAt`, агрегаты —
  по своей политике); долгий диапазон исходных точек и агрегатов: MinIO при
  наличии каталога и читающего
  адаптера. Query Service объединяет границы диапазонов, сортирует и
  ограничивает результат; `cache` — ускорение, не источник истины. При
  недоступности уровня сообщает о частичном результате/отказе явно, не
  подставляет нули и не выдаёт неполную историю за полную.
- Archive Worker до истечения суточного окна ClickHouse записывает в MinIO
  **полные исходные точки отдельно от агрегатов** с `measurementId`, исходными
  именем, значением, единицей при наличии, метками и временем измерения/приёма.
  Проверяет полноту и контрольную сумму, подтверждает каталог `RAW_SAMPLES`,
  **только затем** разрешает удаление соответствующих точек. При сбое архивации
  точки остаются в ClickHouse дольше суток; нужен резерв места и алерт по лагу.
  Безусловный TTL по календарю противоречит FR-013/BR-031. Replay Worker
  проверяет доступность диапазона до запуска, пишет прогресс и возвращает
   данные в тот же конвейер с исходным `measurementId`; для raw старше суток
   используется MinIO в пределах отдельно заданного срока архива. Недоступные
  диапазоны показываются администратору до частичного replay (BR-022).

## Точки отказа и эксплуатационные меры

| Сбой / перегрузка | Предлагаемое поведение и сигнал |
| --- | --- |
| Kafka недоступна / буфер исчерпан | Ingestion не подтверждает приём; контролируемый отказ/ограничение потока, алерт по ошибкам публикации и ёмкости |
| Processing отстаёт | Подтверждённые данные остаются в Kafka в пределах retention, растёт consumer lag; отдельное масштабирование и алерт по p95 свежести |
| ClickHouse недоступен | Storage Writer не подтверждает обработку до надёжной записи; повторяет с backoff; Kafka lag растёт; Query Service явно сигнализирует о недоступной истории |
| Redis `latest` недоступен | Историческая запись продолжает обрабатываться; latest деградирует явно, восстановление/сверка из сохранённой истории до истечения retention |
| PostgreSQL недоступен | Административные изменения и переходы алертов не подтверждаются; повторные попытки оценки не теряют событие при восстановлении |
| MinIO недоступен | Архивация/удаление приостанавливаются; история остаётся в ClickHouse до проверки места и восстановления архива |
| Ошибочный отдельный payload | Ограниченные повторы, карантин с ссылкой на исходные данные и причиной; остальные партиции продолжают работать |

Каждый контейнер публикует readiness/liveness, структурированные логи,
correlation ID и метрики скорости, ошибок, consumer lag, времени актуализации,
глубины outbox, отказов записи и возраста неархивированных данных
(NFR-OBS-001–004). Аудит успешных и неуспешных административных операций
содержит субъекта, время, действие, результат без секретов (NFR-SEC-005).

## Вопросы до реализации

1. **Контракты и безопасность:** заполнить `spec/events.yaml`, OpenAPI и
   ADR-0003: удостоверения отправителя, полномочия на источник, права чтения
   и административные права, версионирование событий/HTTP.
2. **Гарантии Kafka и повторы:** выбрать топологию/replication/acks/retention,
    механизм дедупликации по принятому агентскому `measurementId` при повторе
    и replay, реакцию на изменённое содержимое с тем же ID и атомарность
   записи по каждому приёмнику. Транзакция Kafka **не** атомарна с записью в
   Redis и ClickHouse; `ReplacingMergeTree` удаляет дубли не мгновенно.
3. **Проверка ёмкости:** прежние оценки «1,5–3 байта/точку» и «32 байта/точку»
   не относятся автоматически к полной схеме с UUID, двумя временными
   метками и decimal. Нужны нагрузочный POC, число активных рядов,
   распределение меток, фактические байты/точку, lag и поведение при отказах.
4. **Хранение и архив:** в ADR-0002 каталог архива назван `meta.archive_object`
   (PostgreSQL), но в `spec/database.dbml` указан `archive.archive_object`
   (логическая схема MinIO). Зафиксировать единственного владельца метаданных
   и механизм «полный RAW_SAMPLES-архив подтверждён → выборочное удаление»,
   срок хранения raw в MinIO и работу с поздними точками прежде чем писать миграции.
    Таблица `meta.alert_event_outbox` описана в DBML; уточнить очистку
    опубликованных записей и удержание ожидающих при retention `AlertEvent`.
   Подтвердить в POC, что новые поля `ts.metric_sample` и raw-архив сохраняют
   исходные имя, значение, единицу и метки после нормализации и вне Kafka
   retention; точный способ кодирования исходного значения ещё не выбран.
5. **Правила и актуальность:** протокол обновления конфигурации в работниках,
   поведение при недоступности PostgreSQL, допуск поздних точек, ручной сброс
   при конкурирующей оценке, правила объединения raw/агрегатов и границы
   доступной истории должны пройти проверку сценариями и тестами.
6. **Горячий слой:** в ADR-0002 «последнее значение всегда» и 15-минутный
   RedisTimeSeries с retention описаны вместе; истечение окна после остановки
   источника может удалить и последнюю точку. Нужны отдельное представление
   latest и проверка фактической семантики RedisTimeSeries.
