# User Stories and Use Cases

## Пользовательские истории

### US-001: Отправка метрик

Как владелец наблюдаемого сервиса,  
я хочу передавать системные и прикладные метрики в систему телеметрии,  
чтобы состояние сервиса было доступно для мониторинга и анализа.

#### Acceptance Criteria

- Источник телеметрии идентифицирован.
- Метрика содержит имя, значение и временную метку.
- Система проверяет корректность полученных данных.
- Валидные данные надёжно принимаются для дальнейшей обработки.
- Для отклонённых данных доступна причина ошибки.

Связанные требования: `FR-001`–`FR-004`.

### US-002: Просмотр текущего состояния

Как SRE-инженер,  
я хочу видеть последние значения метрик выбранного объекта,  
чтобы быстро оценить его текущее состояние.

#### Acceptance Criteria

- Пользователь может выбрать метрику и отфильтровать данные по меткам.
- Для каждого временного ряда отображается последнее известное значение.
- Вместе со значением отображается время измерения.
- Отсутствие данных явно отличается от нулевого значения.

Связанные требования: `FR-011`, `FR-014`, `FR-020`.

### US-003: Анализ исторических данных

Как разработчик или SRE-инженер,  
я хочу исследовать метрики за выбранный период,  
чтобы найти причины инцидента или изменения поведения сервиса.

#### Acceptance Criteria

- Пользователь задаёт временной диапазон.
- Данные можно фильтровать по метрике, источнику и меткам.
- Можно запросить исходные или доступные агрегированные значения.
- Результаты возвращаются в хронологическом порядке.
- Большой объём данных не приводит к неограниченному ответу.

Связанные требования: `FR-007`, `FR-008`, `FR-012`, `FR-015`.

### US-004: Построение дашборда

Как руководитель инженерной команды,  
я хочу видеть ключевые показатели сервисов на дашборде,  
чтобы отслеживать их состояние и тенденции.

#### Acceptance Criteria

- Система визуализации может получить временные ряды за выбранный период.
- Данные можно фильтровать по окружению, сервису и другим меткам.
- Ответ содержит значения и соответствующие им временные метки.
- Ошибки запроса возвращаются в машиночитаемом виде.

Связанные требования: `FR-014`–`FR-016`, `FR-020`.

### US-005: Настройка правила алертинга

Как администратор системы,  
я хочу настроить правило алертинга для выбранной метрики,  
чтобы ответственные специалисты узнавали о проблемном состоянии.

#### Acceptance Criteria

- Администратор задаёт метрику, условие, порог и временное окно.
- Некорректное правило нельзя активировать.
- Правило можно включить и отключить без удаления.
- Изменения правила сохраняются с автором и временем изменения.

Связанные требования: `FR-009`, `FR-020`.

### US-006: Получение события об отклонении

Как SRE-инженер,  
я хочу получать событие при выполнении условия алертинга,  
чтобы своевременно начать диагностику проблемы.

#### Acceptance Criteria

- Активные правила проверяются по мере поступления данных.
- Событие создаётся при изменении состояния алерта.
- Событие содержит правило, состояние, время и контекст метрики.
- После нормализации показателя создаётся событие о восстановлении.
- Повторная обработка данных не создаёт неконтролируемые дубликаты.

Связанные требования: `FR-010`.

### US-007: Контроль состояния конвейера

Как администратор системы,  
я хочу видеть состояние приёма, обработки и хранения телеметрии,  
чтобы обнаруживать задержки и отказы самой платформы.

#### Acceptance Criteria

- Доступно состояние работоспособности компонентов системы.
- Отображаются скорость входного потока и количество ошибок.
- Отображаются объём накопленных данных и задержка обработки.
- Видны успешные и неуспешные операции хранения.

Связанные требования: `FR-005`, `FR-019`.

### US-008: Повторная обработка данных

Как администратор системы,  
я хочу повторно обработать ранее принятые данные,  
чтобы восстановить результаты после сбоя или исправления логики.

#### Acceptance Criteria

- Администратор может выбрать диапазон данных для обработки.
- Источникам не требуется отправлять метрики повторно.
- Пользователь видит прогресс и итог операции.
- Проблемные данные изолируются и не блокируют основной поток.
- Повторная обработка не создаёт неконтролируемые дубликаты.

Связанные требования: `FR-017`, `FR-018`, `FR-020`.
