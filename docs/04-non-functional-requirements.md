# Non-Functional Requirements

Нефункциональные требования определяют измеримые свойства системы телеметрии:
производительность, надёжность, доступность, безопасность, масштабируемость и
эксплуатационную пригодность.

Структурированная версия требований находится в
[`spec/non-functional-requirements.yaml`](../spec/non-functional-requirements.yaml).

## Производительность

- Система должна принимать не менее 200 000 метрик в секунду в штатном режиме.
- Система должна выдерживать кратковременные всплески до 400 000 метрик в
  секунду в течение 5 минут.
- 95% последних значений должны становиться доступными не позднее чем через 5
  секунд после приёма метрики.
- 95% событий алертинга должны формироваться не позднее чем через 10 секунд
  после поступления релевантных данных.
- 95% запросов последних значений должны выполняться не дольше 500 мс.

## Масштабируемость

- Система должна поддерживать более 1000 активных источников телеметрии.
- Приём, обработка и запросы должны масштабироваться независимо.
- Должны быть настраиваемые лимиты на размер пакета, количество меток и
  кардинальность.

## Надёжность

- Подтверждённая метрика не должна теряться при отказе одного экземпляра
  компонента.
- Система должна поддерживать повторную обработку ранее принятых данных.
- Проблемные данные не должны блокировать обработку независимых валидных данных.
- Повторная доставка измерения не должна создавать неконтролируемые дубликаты
  доменных результатов.

## Доступность

- Доступность API приёма метрик должна быть не ниже 99.9% в месяц.
- Доступность API чтения метрик должна быть не ниже 99.5% в месяц.
- Плановое обслуживание не должно требовать полной остановки приёма метрик.

## Хранение данных

- Подтверждённые данные должны сохраняться до истечения политики хранения.
- Политика хранения должна отдельно настраиваться для оперативных, исторических
  и архивных данных.
- Удаление данных по истечении срока хранения должно быть контролируемым и
  трассируемым.

## Безопасность

- Все программные интерфейсы должны требовать аутентификации, кроме явно
  разрешённых health-check эндпоинтов.
- Права чтения метрик должны быть отделены от прав административного управления.
- Внешние сетевые взаимодействия должны выполняться по защищённому каналу.
- Секреты, токены и ключи доступа не должны попадать в конфигурацию или логи в
  открытом виде.
- Административные операции должны аудироваться.

## Наблюдаемость

- Компоненты должны публиковать технические метрики о приёме, обработке,
  хранении, запросах и алертинге.
- Компоненты должны предоставлять признаки готовности и работоспособности.
- Ошибки обработки, отказы записи и события алертинга должны логироваться в
  структурированном виде.
- Correlation id должен передаваться по цепочке обработки, если он был передан
  или создан системой.

## Эксплуатация

- Конфигурация правил алертинга, политик агрегации, лимитов и сроков хранения
  должна изменяться без пересборки системы.
- Критичная конфигурация должна валидироваться до применения.
- Система должна поддерживать поэтапное обновление компонентов без полной
  остановки платформы.
- Операции повторной обработки должны иметь прогресс, итог и возможность
  безопасного повторного запуска.

## Совместимость

- Публичные API должны быть версионированы.
- Несовместимые изменения API должны вводиться через новую версию.
- Форматы входящих и исходящих данных должны быть документированы и пригодны для
  автоматической валидации.
